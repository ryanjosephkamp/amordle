Exact annotations and normalized requirements

ANNOT-01 Notifications desktop alignment

Notifications text spacing issue on desktop view:
Please add a bit more space/separation between match status (e.g., “Match ready”, “Your turn”, etc.) and the date (e.g., “8/2/2026”).

We could even align these into a more tabular looking format, such that the statuses are always aligned, the dates are always aligned, and the times are always aligned.

Normalized: separate and consistently align status, date, and time on desktop while retaining responsive behavior, routing, read state, and Mark All Read.

ANNOT-02 Active Solo desktop structure

On desktop:
This looks too crowded and not quite polished enough.
This “active solo” table content is poorly aligned or structured.
We absolutely need to fix it.

Normalized: create a clear, scannable desktop session layout with predictably aligned identity, progress, Resume, and Abandon controls without regressing mobile or session semantics.

ANNOT-03 Active Solo light-button foreground

Grey on white is still hard to read.
Please improve readability.
We can use a darker grey or black or something.

Normalized: use the established high-contrast dark foreground on light Resume buttons, including disabled state.

ANNOT-04 Choose-how-to-play white-on-white

wtf, this is literally white text on white background…
impossible to read!
please fix this immediately

Normalized: repair the Set Up Solo action as part of a systemic light-surface contrast correction.

ANNOT-05 Equal Players filter heights

These rectangular boxes (“Player name”, “Rating lane”, “Minimum rating”, “Maximum rating”, “Sort”) and buttons (“apply”) should all be the same height.

Normalized: normalize filter input/select/action heights and baselines while preserving labels, touch targets, focus, and responsive wrapping.

ANNOT-06 Serious Stats overhaul

We need to do a serious overhaul on the Stats page.

First, I want better visualizations.
These bars/meters/etc. are insufficient. We can keep some of them, but we need actual graphs, charts, and other relevant content to truly visualize the stats in a cool way.

Second, I don’t really know why some content spans the full width of the page while other content doesn’t here.
Specifically, the ranked ratings info has a bunch of blank space to the right of it.

Also, the ranked ratings should show Elo and stats for all of the different ranked game modes; I can’t currently tell from here whether the ranked ratings info is for ranked OG, ranked GO, or whatever

Normalized: map the actual durable data first; add truthful accessible graphs/charts; normalize widths; show and unambiguously label every real ranked bucket; never fabricate buckets or time series.

ANNOT-07 Marketplace white-on-white

There’s more white font on white background!
This is impossible to read!
Please fix this everywhere in the site so that we never, ever, EVER have white on white like that.

Normalized: include Marketplace in a complete sitewide light-surface contrast audit.

ANNOT-08 Centered and dismissible dialogs

Settings on desktop:

The “change email”, “change password”, and danger zone popovers all appear in the upper left corner of the page.

This is not consistent with the other Profile popovers (e.g., configuring accent colors, etc.) that appear in the center of the page.

All popovers like these should appear in the center of the page.

Additionally, to close these popovers, the player should be able to click the “x” button in the top right (like they currently can) OR they can simply click outside of the box.

I want all popovers across the entire site to have that same policy, where clicking outside of the popover box will automatically close the popover.

Normalized: center true modal dialogs and standardize safe X, backdrop, and Escape dismissal with focus restoration. Audit dialog/menu/tooltip distinctions and destructive pending states.

ANNOT-09 Canonical dark foreground

On the Profile page:

Look at the dark/black font color that you’re using for these accent color (e.g., “Amber”) and “save profile” texts when the button background is light/white.

This is the PERFECT dark font color to use for button text where the background is light/white like that.

So, please carefully inspect all site pages and then ensure that instead of a light grey or some other color, we are always using this same exact dark/black font color for text within buttons with light/white backgrounds.

Normalized: make the existing Profile dark foreground the central design-token authority for every light/white control and descendant label.

ANNOT-10 Successful sign-in goes Home

When I sign in to an account, this is the type of page that appears.

I actually would prefer that we have the game automatically go to the home page, rather than to this page, upon successful player sign in.

That way, the player doesn’t have to manually go to the home page or to some other site page in order to do what they actually want immediately after sign-in.

Normalized: Home is the default ordinary sign-in destination; audit and preserve only intentional safe return/deep-link/recovery behavior.

ANNOT-11 Account navigation names the player

I want to replace the “account” text in the account button at the top of the site with the signed-in player’s player name. For this specific example account here, that would replace “account” with “ragnar”.

If a player is signed out, then this should say something like “guest”.

This would make it very clear that the player is signed in at any time and on any page of the site.

Perhaps if the player hasn’t configured their own player name yet, we can just show the first several (you choose the exact number) characters of the account’s email address, e.g., for a private address, this could be “player…” or something, so that we don’t have spillover and so that the button doesn’t get ridiculously big.

Please use your best judgment about this.

Normalized: show player name, then a bounded owner-only email-derived fallback, or Guest; handle hydration, edits, account switching, truncation, accessibility, and privacy.

ANNOT-12 Every definition names its word

I forfeited this ranked COMBAT match.
Notice how the actual solution isn’t shown below the gameplay area, but its definition is…
We need the actual solution to be shown alongside all definitions that are shown, across the entire game—across all game types, etc.

The rule should be that if a player is shown a definition of a word, then the word itself must also always be shown in the same definition area.

Normalized: whenever a definition is already authorized and rendered, that region must visibly name its word. This must never widen answer authority or reveal a word early.

Cross-cutting planning requirements

  • Contrast: one canonical dark foreground for light controls; 4.5:1 ordinary text and 3:1 meaningful borders/icons/focus; readable disabled states; forced-colors support; semantic evidence colors unchanged.
  • Responsive structure: Notifications, Active Solo, Players filters, Stats, and Account labels must contain cleanly at 320–1920 widths and 200% zoom without document overflow or collisions.
  • Stats integrity: every visualization must be sourced from durable or explicitly pending data and have a textual equivalent. No invented bucket or time series.
  • Overlay semantics: modal dialogs are centered; anchored menus remain anchored; destructive pending work cannot be dismissed ambiguously.
  • Identity safety: no stale label from another account, no public email projection, no redirect loop or foreign open redirect.
  • Answer privacy: the definition-word invariant applies only after existing reveal authority permits the definition.

Boundaries

  • No implementation, commit, push, deployment, service mutation, or data creation is authorized by this intake.
  • No game-rule, scoring, answer, evidence, rating-algorithm, economy, matchmaking, persistence, settlement, or word-list change is requested.
  • No migration, API, paid capability, vendor, or chart dependency is presumed.
  • Production, the default branch, real accounts, existing E2E profiles, immutable migrations, and the locked shell remain untouched.
