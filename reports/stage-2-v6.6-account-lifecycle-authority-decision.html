Why new authority is required

Signed-in email and password changes can use Supabase Auth's existing updateUser authority after reauthentication. Destructive account actions cannot securely run in the browser. They require a bounded service that verifies the password, issues one-time confirmations, preserves opponent-side shared facts, removes an avatar, and invokes administrative Auth deletion without exposing the service-role credential.

Migration authority

Private confirmation records

The new private table stores only token hashes. Each challenge is bound to one user and one enumerated action, expires after five minutes, and is serialized with a per-account advisory lock. Non-account-deletion actions are consumed once. Permanent deletion enters a private cleanup-only processing state until Storage and Auth finish. Issuance is bounded to five recent attempts in fifteen minutes. Browser roles receive no table or function access.

Competitive generations

A private generation marker supports a fresh personal 1200/provisional/zero W-L-D rating generation without erasing settled matches or opponent evidence.

Shared facts

Settled multiplayer participant references become nullable and retain stable seat keys. Account deletion replaces personal display data with Deleted player while preserving opponent History and rating integrity. Pending queues, reservations, requests, and unfinished account-owned claims are removed first.

Destructive scopes

  • Delete Solo history and progress: removes Solo sessions, History, statistical sources, streak, and pending Solo completions; preserves economy, purchases, settings, and COMBAT.
  • Restart competitive profile: refuses during active COMBAT, cancels waiting state, hides the requesting player's pre-reset personal COMBAT History, and starts fresh rating buckets; preserves settled shared facts and opponent data.
  • Delete account permanently: refuses during active COMBAT, removes personal data, detaches settled participant facts, deletes the exact avatar, then deletes the Auth user. Browser caches are cleared only after success.

Edge Function contract

account-lifecycle-v1 accepts authenticated POST requests up to 4096 bytes. Its only operations are prepare with the current password and confirm with the one-time token. It reauthenticates in a non-persistent client, generates a 256-bit token, persists only its SHA-256 hash, calls only service-role lifecycle procedures, and returns sanitized receipts. The source has no logging statements.

Database confirmation enters a private processing state and retains the exact avatar cleanup receipt before Storage or Auth deletion. The same confirmation can retry only that idempotent external cleanup; an expired or closed confirmation requires fresh password verification and inherits only the pending receipt. Avatar paths must belong to the linked project's exact public avatar bucket. Storage deletion receives at most three exact retries; Auth deletion occurs only after Storage succeeds. Residue or a partial cross-service failure blocks completion and requires exact cleanup or a forward repair.

HTTP contract reconciliation

The three Next.js application interfaces remain unchanged. The proposed Edge Function is one separate authenticated Supabase service surface, limited to two operations and three actions. It is not a general administrative API and does not authorize service-role browser access, another vendor, another project, or Production mutation.
